# ABDM M2/M3 Integration — Technical Documentation

## Care Context Linking, Consent Management, and Health Information Exchange

---

## 1. Overview

This document describes the complete data flow implemented in this project, from the creation and linking of ABDM care contexts through to the decryption of health information by a Health Information User (HIU). The system integrates with Ayushman Bharat Digital Mission (ABDM) infrastructure via Eka Care's API layer.

### 1.1 Roles

Two distinct roles participate in this exchange:

| Role | Definition | Responsibility in this system |
|---|---|---|
| **HIP** (Health Information Provider) | The entity holding the patient's clinical data — in this case, the hospital/facility. | Creates and links care contexts; on request, builds, encrypts, and transmits health records. |
| **HIU** (Health Information User) | The entity requesting access to a patient's clinical data. | Requests consent from the patient; on approval, receives and decrypts the transmitted records. |

Because this deployment is under active development and testing, a single account operates in **both** roles simultaneously. In a production deployment, the HIU would typically be a separate registered entity (a different hospital, a diagnostic aggregator, an insurer, etc.).

### 1.2 Milestones

| Milestone | Scope | Status in this system |
|---|---|---|
| **M1** | ABHA (Ayushman Bharat Health Account) creation and authentication. | Complete. Not covered in detail in this document. |
| **M2** | Care Context Linking and Data Sharing — the HIP-side workflow. | Complete. Documented in Sections 3 and 4. |
| **M3** | Consent Management and Health Information Exchange — the HIU-side workflow. | Complete. Documented in Sections 5 and 6. |

### 1.3 Data Model

All state is maintained in a single flat table (`data/master_flat_table.csv`), keyed by `record_id`. A single `patient_id` may correspond to multiple `record_id` values, one per encounter or care context. The schema is organized into four logical groups:

| Group | Contents | Origin |
|---|---|---|
| **A — Identity** | ABHA address, ABHA number, patient name, demographics, `eka_patient_id` (OID). | Extracted automatically from the M1 authentication response. |
| **B — Clinical source** | Symptoms, vitals, diagnosis, medications, lab results, and related clinical fields. | Supplied manually or via HIS integration. |
| **C — Care context** | `hi_type`, `care_context_id`, `display`, and link status fields. | Generated by the Phase 1 pipeline. |
| **D — Consent and transfer** | Consent status, consent artifact reference, bundle transfer status. | Populated during Phase 2 processing. |

## 2. Prerequisites and Configuration

### 2.1 Environment Variables

Configuration is read exclusively from environment variables (via a `.env` file), never hardcoded. Required values:

```
EKA_ENV=sandbox
EKA_BASE_URL=https://api.dev.eka.care
EKA_CLIENT_ID=<client id>
EKA_CLIENT_SECRET=<client secret>
EKA_HIP_ID=<facility HIP identifier>
EKA_HIU_CLINIC_ID=<HIU clinic identifier, if acting as HIU>
```

### 2.2 Authentication

All API calls authenticate via a bearer token obtained through Eka's Connect Login API:

```
POST /connect-auth/v1/account/login
Body: {client_id, client_secret}
Response: {access_token, expires_in, refresh_token, refresh_expires_in}
```

The token is cached in memory and refreshed automatically shortly before expiry. Note: session continuity matters — forcing a fresh login mid-workflow (for example, immediately before a consent approval) has been observed to invalidate the session context associated with prior steps and should be avoided.

## 3. Milestone M2, Phase 1 — Care Context Creation and Linking

### 3.1 Purpose

Phase 1 establishes a record of a clinical encounter with ABDM and links it to the patient's ABHA address, without transmitting any clinical content at this stage.

### 3.2 Sequence

1. **Record initialization.** `get_or_create_record(patient_id, encounter_id)` establishes the idempotency boundary: the same `(patient_id, encounter_id)` pair always resolves to the same `record_id`. A new `encounter_id` for an existing patient produces a new record.
2. **Identity population.** `add_or_update_identity_from_m1()` extracts ABHA address, ABHA number, and OID from the stored M1 authentication response.
3. **Clinical data entry.** `set_clinical_data()` populates Group B fields for the encounter.
4. **Care context generation.** `generate_care_context()` assigns a `care_context_id` and human-readable `display` string for the given `hi_type`.
5. **Link request.** `eka_client.link_care_context()` submits the request.
6. **Asynchronous confirmation.** The Link API returns `202 Accepted`, indicating the request has been received for processing — not that linking is complete. Final status arrives via the `abha.link_care_context` webhook.

### 3.3 API Specification

```
POST /abdm/v1/care-contexts/link
Headers: X-Pt-Id, X-Partner-Pt-Id, X-Hip-Id, Authorization
Body: {
  abha_address,
  care_contexts: [{care_context_id, display, hi_type}],
  oid,
  partner_user_id
}
```

`oid` and `partner_user_id` are required in the request body in addition to their corresponding header values.

### 3.4 Webhook Confirmation

```
Event: abha.link_care_context
Payload (nested under "data"): {
  abha_address, hip_id, care_context_id, status, error, retry_count, oid, partner_patient_id
}
```

`status` is either `LINKED` or `ERRORED`. The webhook handler locates the corresponding record via `care_context_id` and updates `link_status`, `link_error`, and `linked_at` accordingly.

## 4. Milestone M2, Phase 2 — Health Information Data Fetch (HIP Response)

### 4.1 Purpose

Phase 2 governs the HIP's response when an HIU requests data for a previously linked and consented care context.

### 4.2 Trigger

Per Eka's documented guarantee, the `abha.hip_data_fetch` webhook is dispatched **only after** the relevant consent has been verified upstream by the ABDM gateway. Consequently, the arrival of this webhook is itself treated as authoritative confirmation of consent — it is not preceded by, or dependent upon, any locally-set consent flag.

### 4.3 Sequence

1. The webhook payload is parsed; `transaction_id` is read from the **nested** `data.transaction_id` field (distinct from, and not to be confused with, the outer envelope's `transaction_id`).
2. For each `care_context_id` in `data.care_contexts`:
   a. The corresponding record is located via `find_row_by_care_context_id()`.
   b. Consent is recorded locally (`set_consent()`), using the transaction reference as the consent artifact identifier.
   c. `check_consent_before_bundling()` performs a final safety-net verification.
   d. `fhir_builder.build_bundle(row)` constructs the FHIR R4 document bundle.
   e. A SHA-256 checksum of the **plaintext** bundle is computed.
   f. The bundle is encrypted (see Section 7).
   g. The encrypted content is transmitted via `eka_client.push_on_fetch_response()`.

### 4.4 API Specification

```
POST /abdm/v1/hip/care-context/data/on-fetch
Headers: X-Pt-Id, X-Partner-Pt-Id, X-Hip-Id, Authorization
Body: {
  entries: [{care_context_id, checksum, content, media: "application/fhir+json"}],
  key_information: {crypto_alg, curve, dh_public_key: {expiry, key_value, parameters}, nonce},
  page_count, page_number, transaction_id
}
```

`checksum` is calculated over the plaintext content prior to encryption. `content` contains the encrypted bundle. `key_information` reflects the HIP's own newly generated key material for this exchange — not the requester's.

## 5. Milestone M3 — Consent Lifecycle Management (HIU Role)

### 5.1 Purpose

This stage governs the HIU-side request for access to a patient's health information, culminating in a granted consent artifact.

### 5.2 Sequence

1. **Consent creation.**
   ```
   POST /abdm/v1/consents/create
   Body: {care_contexts, hip_identifier, patient, period, purpose, record_types}
   Response: {consent_init_id}
   ```
   `care_contexts` and `hip_identifier` must be included at creation time; their omission has been observed to produce validation failures at the approval stage.

2. **Consent lookup.**
   ```
   POST /abdm/v1/consents/list
   Body: {hiu: {clinic_id[, d_oid]}, patient: {health_id, oid}}
   Response: {consents: [{consent_init_id, consent_id, status, hi_types, period}]}
   ```
   `consent_init_id` and `consent_id` are distinct identifiers. The list endpoint is polled until the newly created consent (matched by `consent_init_id`) appears, yielding the `consent_id` required for approval.

3. **Consent approval.**
   ```
   POST /abdm/v1/consents/approve?oid=<patient_oid>
   Body: {id, consent_artefacts: [{access_mode, care_contexts, duration, erase_at, hi_types, hip_id}], access_mode, duration, erase_at, hi_types}
   ```
   Successful approval returns `204 No Content`. The same authenticated session used for creation and lookup must be used for approval; obtaining a new token immediately prior to this call has been observed to produce a session-state error.

4. Upon approval, Eka assumes responsibility for the remaining ABDM gateway callbacks required to initiate data transfer — no further action is required on the HIU side to trigger the HIP's data-fetch flow described in Section 4.

### 5.3 Data Validation

The `eka_patient_id` (OID) field is a long numeric string and is susceptible to corruption if the underlying data file is opened and saved in spreadsheet software without the relevant column explicitly formatted as text (resulting in scientific-notation representations such as `1.78789E+14`). A validation check (`validate_oid()`) is applied prior to consent creation to detect this condition and fail with a diagnostic message rather than submitting malformed data to the API.

## 6. Milestone M3 — Data Reception and Decryption (HIU Role)

### 6.1 Key Registration

Prior to any consent-based data exchange, the HIU's public key material must be registered with Eka so that it can be relayed to HIPs for encryption:

```
PATCH /abdm/v1/hiu/keyset
Body: {public_key, nonce}
```

In this implementation, a fresh key pair is generated and registered automatically at each startup of the webhook server. The corresponding private key is retained in memory for the duration of that process and is required to decrypt any data subsequently received.

**Operational constraint:** because key material is regenerated at every server restart, a restart occurring between consent approval and data receipt will render the previously registered public key — and any data encrypted against it — undecryptable. Continuous operation between approval and receipt is required.

### 6.2 Reception

```
Event: abha.hiu_data_push
Payload: {data: {entries: [{care_context_id, content, checksum, media}], key_information}}
```

For each entry, `decrypt_incoming_payload()` is invoked using the HIU's own private key together with the sender's (HIP's) nonce and public key, as supplied in `key_information`. The resulting plaintext is parsed as JSON and persisted to `decrypt-hiu/<care_context_id>.json`.

---

## 7. Cryptographic Architecture

### 7.1 Algorithm

Encryption is performed using Elliptic Curve Diffie-Hellman (ECDH) key exchange over Curve25519, with HKDF-SHA256 key derivation and AES-256-GCM symmetric encryption, via the `abdm-ecdh` reference library.

### 7.2 Principle of Operation

Each party generates an independent key pair and a nonce. A party encrypting data combines **its own private key** with **the counterparty's public key** to derive a shared secret; the counterparty, decrypting, combines **its own private key** with **the originating party's public key**. Both derivations yield an identical shared secret by construction of the algorithm. At no point is the shared secret itself transmitted; only public keys and nonces cross the network.

### 7.3 Application in This System

| Direction | Encrypting party | Private key used | Public key used |
|---|---|---|---|
| HIP → HIU (Section 4) | HIP | HIP's freshly generated key, this exchange only | HIU's public key, from the `abha.hip_data_fetch` payload |
| HIU decryption (Section 6) | — | HIU's registered key, retained since server startup | HIP's public key, from the `abha.hiu_data_push` payload |

### 7.4 Integrity Verification

A SHA-256 checksum of the plaintext bundle is computed and transmitted alongside the encrypted content, prior to encryption. This allows the receiving party to verify content integrity after decryption independently of the encryption mechanism itself.

## Appendix B — Webhook Event Reference

| Event | Direction | Purpose |
|---|---|---|
| `abha.link_care_context` | Inbound to HIP | Confirms or denies a care context link request |
| `abha.hip_data_fetch` | Inbound to HIP | Requests data transmission for one or more linked, consented care contexts |
| `abha.consent_update` | Inbound to HIU | Notifies of a change in consent status |
| `abha.hiu_data_push` | Inbound to HIU | Delivers encrypted health data following an approved consent |
| `abha.discover_care_context` | Inbound to HIP | Discovery flow notification (not yet implemented in this system) |

## Appendix C — Known Limitations and Unconfirmed Items

- Webhook signature verification is not yet implemented; the current handler accepts all incoming requests without cryptographic validation of origin.
- The `dh_public_key.expiry` field's expected format is not documented and is currently transmitted as an empty string.
- `DiagnosticReport` bundle construction does not yet model a complete `DiagnosticReport`/`ServiceRequest` resource pair.
- The discovery flow (`abha.discover_care_context`) is received but not processed.
- Webhook registration for ABDM-specific events (as distinct from appointment/prescription/receipt events) has no self-service API and must be coordinated directly with Eka Care.
